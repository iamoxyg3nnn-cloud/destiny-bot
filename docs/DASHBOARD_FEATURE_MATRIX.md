# Dashboard feature matrix

The “Current implementation” column records the initial local audit on 2026-11-12. Dashboard API/UI status in “Work required” reflects progress through 2026-11-13. “Missing” means no dashboard-facing implementation is present, even when the bot domain service or database capability exists.

| Feature | Current implementation | Database support | Existing API support | Dashboard requirement | Work required |
|---|---|---|---|---|---|
| Anonymous matchmaking | Discord slash commands, Postgres-backed queue state/locks, room lifecycle | users, rooms, messages, blocks; schema hardened by migrations 016–019 | None | Preserve existing matching behavior; only expose guild scope controls supported today | Keep bot/domain path; add authenticated API separately |
| Portal channel | `/setup portal`, Discord channel select, guild-scoped authorization | `guild_settings.match_channel_id` | Guild-scoped GET/PUT; validates live bot view/send/embed permissions; conditional update uses `updated_at` | View, choose, validate, save, reset | Production OAuth setup; audit write is separate from setting write; no transactional outbox |
| Cross-server participation | `/setup cross_server`; matchmaking uses stored guild settings while preserving unscoped DM behavior | `guild_settings.cross_server_enabled` (default true) | Guild-scoped GET/PUT; conditional update uses `updated_at` | View and change participation | Production OAuth setup; audit write is separate from setting write; no transactional outbox |
| Private moderation log channel | `/setup modlog`; trusted-staff delivery logic | `guild_settings.mod_log_channel_id` | Guild-scoped GET/PUT; validates live bot view/send permissions; conditional update uses `updated_at` | Configure privately, separately from portal | Production OAuth setup; audit write is separate from setting write |
| Guild configuration export | No existing dashboard flow | Current `guild_settings` fields only | Guild-scoped export requires fresh membership and current bot snapshot, emits supported fields only, and withholds the export if audit writing fails | Download a safe configuration backup | Import/restore is not implemented; exported file is a reference/backup only |
| Guild setup status | `/setup view` and setup panels | `guild_settings` row | Server dashboard derives bot connection, settings and channel permissions from fresh sources | Overview and onboarding grounded in real status | Manager roles, integrations and deeper diagnostics are not implemented |
| Guild manager roles | Current access checks fresh Discord owner/Administrator/Manage Server bits; `guild_settings.allowed_roles` has no active authorization use in source | Legacy `allowed_roles` column only; no dedicated assignment model | None | Fine-grained delegated guild roles | Official current-user member endpoint offers fresh role IDs with the additional `guilds.members.read` consent scope; still needs capability model, persistence, revocation behavior, migration and audit; do not repurpose `allowed_roles` |
| Guild configuration audit | Setup events written by bot and dashboard | `admin_audit_logs` (server-side only) | Paginated guild-filtered API checks fresh Discord manager membership and suppresses IP metadata; dashboard setting events can be rolled back when their recorded `next` value is still current | Guild-isolated history with actor/action/result and safe rollback | Rollback covers only the three supported dashboard setting actions; bot-command events and audit/version transactions remain unsupported |
| Server notifications | User reminder preferences exist; no guild notification settings surfaced | `notification_settings` is user-scoped | None | Only server-level settings if they exist | Do not create switches; audit actual notification behavior first |
| Global owner allowlist | `BOT_OWNER_IDS`, comma-separated, validated at config load | Environment configuration | Owner dashboard login, root-only operator management, and root bypass for all capabilities | Independent owner dashboard login and immutable recovery owners | Separate session secret and namespace, audit login, root allowlist; production OAuth setup remains |
| Delegated platform operators | Named global capabilities; roots remain independent | `platform_operator_grants` and transactional `set_platform_operator_capability` RPC in migration 020 | Root-only list/grant/revoke; capabilities are checked on every request and revoke takes effect immediately | Scoped global permissions with audit-backed grant/revocation | Migration 020 validated on isolated Supabase project; apply only as a reviewed production deployment step |
| Global system diagnostics | `/owner status`: Supabase runtime state and shard/worker counts when discoverable | Supabase-backed heartbeats/snapshots and database connectivity | Owner dashboard reports services, aggregate counts, individual worker/shard status | Actual health with unavailable distinct from zero | Queue metrics, API version, CPU/memory and recent errors remain unimplemented |
| Global server inventory | Discord bot publishes guild snapshots to Supabase with name/icon/member count | Snapshot plus `guild_settings` | Owner-only search/list and verified detail API reads live bot permissions and saved configuration | Search connected servers, inspect configuration and bot access | Join/leave history and safe restriction actions are not implemented |
| Users and restrictions | Profile, ban policy, temporary/permanent safety restrictions | `users`, report and moderation fields | Root-owner or `users.status.lookup` exact Destiny/Discord ID lookup with audit-on-access and minimal restriction/verification status; read-only | Privacy-minimized global owner workflows | Safe global restriction mutation is not exposed; use case-scoped report resolution until a dedicated domain workflow exists |
| Reports and safety cases | Report submission, alert delivery, atomic report resolution | `reports`, `users`, `rooms`; report may include chat excerpt | Root-owner or `safety.reports.review` queue lists case metadata; case detail reveals pseudonymized excerpt; resolution reuses atomic DB function and records rationale/audit | Owner-only safety queue and resolution | Audit-write transactionality and evidence retention review remain |
| Anonymous room operations | Room lifecycle, private DM relay | `rooms`, `messages` | Root-owner or `conversations.metadata.read` paginated active-room inventory returns room codes, pseudonyms, and timing only; reads are audited | Minimal metadata and controlled termination only if safe operation is added | No message content, account IDs, or termination action; add termination only as a case-scoped audited workflow |
| Verification | Submission/review flows and staff alerts | Existing user verification status/evidence fields | Root-owner or `safety.verification.review` queue exposes Destiny ID and submission time; case view reveals evidence; approve/reject reuses existing review service and audit behavior | Owner/global reviewer workflow | Evidence retention review remains |
| Queue/worker controls | Polling workers and Supabase-backed heartbeats | Supabase runtime coordination state | Owner overview/monitoring reads worker freshness | Real worker diagnostics | Durable job queue, bounded job detail, stalled-job controls, safe retry, and queue-specific integration remain unimplemented |
| Economy/progression/Icebreaker | Retired; repository migration 016 deletes economy/progression data/schema | Historical migrations only | None | Must remain absent | Never reintroduce or expose legacy tables/features |
